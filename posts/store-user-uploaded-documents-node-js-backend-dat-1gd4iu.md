# Store User-Uploaded Documents: Node.js Backend Database or Object Storage?

Short answer: for a property-management system, the backend I would use to store user-uploaded documents and generated reports for authenticated customers keeps tenant ownership, authorization state, and document metadata in the database, while private object storage holds the bytes unless a small-file, single-transaction requirement outweighs independent recovery. The cheapest option is the one whose isolation and restore behavior you can operate inside the SLO, not the one with the lowest storage line item.

I would make tenant isolation the decision axis before comparing blob prices. A report can be perfectly durable and still be a security incident if a download path accepts a document ID without proving that the requesting customer may read that document. Byte placement is secondary to the ownership check.

## What must a property report backend prove before it stores bytes?

The production scenario to rehearse is bounded and ordinary: a customer signs in, asks for a monthly property report, and receives a file generated by a background job. The report belongs to tenant `north-17`; the request includes a valid session, but the database query accidentally filters only on `document_id`. A guessable identifier, a stale cache entry, or a copied download URL can then turn authentication into a false sense of safety. Authentication answers “who is calling?” Authorization must answer “which tenant's document may this caller read?”

That invariant belongs beside the metadata lookup, not in a later file-serving layer. I write the rule as: resolve `(tenant_id, document_id)` from the database, verify the caller's tenant and permission, then resolve the immutable object key. The object key is not an authorization token. It is only a storage location.

The failure is easy to miss because most happy-path tests use one tenant. My minimum fixture has three tenants, two documents with similar filenames, an expired customer account, and a request that returns 403 rather than revealing whether another tenant's document exists. It also exercises a report that is generated but not yet available. Short test. Important boundary.

## Start with the recovery and isolation SLO

For large user-uploaded documents, object storage usually gives the cleaner capacity boundary. The database stores a document row with tenant ID, owner, filename, media type, byte count, checksum, lifecycle state, and object key. The object store holds the bytes. A Node.js service can authenticate the request, perform the database authorization query, and stream or redirect the approved download without making the object store responsible for tenant policy.

Database blobs still have a legitimate shape. If reports are small, short-lived, and required to commit atomically with the business row, keeping the payload in the same transactional system can reduce coordination. That choice is easy to explain to a small team: one transaction, one backup boundary, one query model.

The trade-off appears during recovery. A database backup that includes a growing archive of PDFs, spreadsheets, and scans makes the relational recovery path carry every byte before the application is whole. That can consume restore bandwidth and storage capacity that the database SLO never counted. Object storage separates the large transfer from the database's recovery boundary, but it introduces a second write and a reconciliation problem. There is no free option.

This is where a capacity plan becomes more useful than a price table. Suppose a report job creates a 40 MB packet for each building every month, and the property manager retains seven years of history; the exact figures will differ, but the multiplication is the point. The database design carries those bytes through primary storage, replicas, backup copies, restore staging, and the operational checks that prove the backup is usable. The object design still pays to store and transfer them, yet the database restore can recover tenant rows and authorization state without first moving the entire report archive. During a partial recovery, the application can represent a report as `pending` or temporarily unavailable instead of treating a half-restored binary column as a valid document. That separation does not remove the availability problem; it makes the problem visible in the document state and gives the on-call engineer a bounded queue to drain. I would put the byte-growth estimate, restore throughput, retention rule, and cleanup interval in the same review as the schema, because each one changes the actual SLO.

## Should Node.js store user-uploaded documents in database blobs or object storage?

The safe workflow has two explicit states: `pending` and `ready`. Create the metadata row with its tenant ID before or alongside the upload intent, write to a newly generated object key, verify the completed object, and mark the row ready only after the application has enough evidence to serve it. A failed or abandoned attempt remains distinguishable from a document that is safe to return.

The read path should make the authorization decision before it asks for bytes. Here is the shape I want reviewed in a Go service; the same boundary applies to a Node.js implementation.

```go
package documents

import (
	"context"
	"errors"
)

var ErrForbidden = errors.New("document access denied")

type Document struct {
	TenantID string
	ObjectKey string
	State    string
}

type Repository interface {
	Find(ctx context.Context, tenantID, documentID string) (Document, error)
}

type ObjectReader interface {
	Open(ctx context.Context, key string) (Reader, error)
}

type Reader interface {
	Read([]byte) (int, error)
	Close() error
}

func OpenForCustomer(ctx context.Context, repo Repository, objects ObjectReader, tenantID, documentID string) (Reader, error) {
	doc, err := repo.Find(ctx, tenantID, documentID)
	if err != nil {
		return nil, err
	}
	if doc.TenantID != tenantID || doc.State != "ready" {
		return nil, ErrForbidden
	}
	return objects.Open(ctx, doc.ObjectKey)
}
```

The repository query should enforce the tenant predicate itself; checking a field after a broad lookup is weaker than making cross-tenant rows unselectable. Log the tenant, document, authorization result, and request ID, but do not log the report contents or a customer-supplied path. Measure authorization failures separately from missing documents so a sudden change is visible without exposing another tenant's existence to the caller.

For downloads, private access and a short-lived delegated URL can be reasonable, but the URL must be minted only after the same authorization check. `Cache-Control` matters here: a response carrying a customer report should have an explicit caching policy, because a shared cache is another place where tenant boundaries can be crossed. The browser and intermediary behavior described by MDN is a reminder to decide this deliberately, not to inherit a framework default. (See References.)

Deletion deserves the same discipline. GDPR Article 17 describes a right to erasure, so deletion needs an auditable state transition for the metadata and the bytes, including retries and cleanup of objects whose database row is gone. A successful database delete with an orphaned report is not the same outcome as erasure. I am not sure one universal retention interval can fit every property manager; legal retention, customer contracts, and backup expiration need an explicit review.

## Compare the choices by recovery and on-call work

I use a buy-vs-build table that asks what the platform team must operate, because a low byte rate does not compensate for an RTO that nobody can meet.

| Choice | Isolation and recovery shape | Sensible fit | Move away when |
|---|---|---|---|
| Database blob | Authorization is close to the business row; backup and restore carry the payload with relational data | Small reports and a strong atomic-commit requirement | File volume materially changes database size or restore time |
| S3-compatible object storage | Private objects have an independent capacity boundary; the service owns the metadata-to-key join | Large reports, multipart transfers, and independently managed retention | The team cannot operate reconciliation, lifecycle cleanup, and access policy |
| Self-hosted object storage | The same object model can be kept behind a private network, but the team owns disks, replication, upgrades, and recovery | An established stateful-service team with capacity to run storage | On-call coverage and failure drills are thinner than the storage SLO |

The row I care about most is the last column. Object storage is not automatically suitable for every property-management workflow: strict atomicity across a report row and its bytes, immutable retention requirements, or a team with no spare operational capacity may justify a database-backed design or a managed service with the required controls. Stick with the database when its transaction boundary is a product requirement and the measured file corpus fits the recovery budget. Choose a different object system when lifecycle, legal hold, versioning, or private-network requirements are non-negotiable.

Cost still belongs in the review, but as total ownership: storage, requests, egress, backup copies, restore testing, on-call time, and the engineering effort required to reconcile two systems. I'm not sure a vendor price comparison can answer that without your retention and download distribution. Model those inputs instead. A spreadsheet that says “cheap per gigabyte” is not a capacity plan.

Your mileage may vary.

## Make the SLO testable before choosing a backend

Set separate objectives for report generation, authorized download latency, tenant-isolation correctness, and recovery. A useful exercise is to estimate the 95th and 99th percentile report sizes, monthly growth, concurrent downloads, retention duration, and the bytes that must be restored for a database-only design. Then run a restore drill and a cross-tenant test against the same release candidate. If the design cannot demonstrate the target RTO and a 403 for an unauthorized tenant, it has not passed review.

The operational checklist is short enough to keep next to the design record:

- Generate a non-reused object key; never let a customer choose the storage namespace.
- Require tenant-scoped authorization for every metadata lookup and download delegation.
- Keep `pending`, `ready`, and deletion states observable and reconcile them on a schedule.
- Set explicit `Cache-Control` headers for authenticated report responses.
- Test restore, orphan cleanup, expired links, duplicate uploads, and cross-tenant access.
- Alert on reconciliation age and storage growth, not only HTTP latency.

The decision rule is therefore specific to this system: for authenticated property reports, use the database as the tenant-scoped authority and object storage as the byte boundary when the corpus is large enough to affect database recovery. Use blobs when atomicity and small scale win. Either way, make tenant ID part of the lookup contract, make the cache policy explicit, and prove the recovery and erasure paths before calling the backend cheap.
